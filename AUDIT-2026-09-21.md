# quanta-memory-platform 시스템 코드 감사

감사일: 2026-09-21  
대상 저장소: `quanta-memory-platform`  
동결 소스: `e103771670da3143e2ffebb8950a5dfc7e3d4515` (`main`)  
감사 방식: 읽기 전용 정적 추적 + 현재 소스 테스트/게이트 실행 + 실제 standalone 추출 + 외부 host 정적 연결 추적

## 1. 최종 판정

**목적 적합성: FAIL — production-ready / extraction-ready로 닫을 수 없다.**

이 저장소가 의도하는 핵심은 다음 세 가지다.

1. host-independent한 메모리 예산/회계 라이브러리
2. 하나의 ledger 권위가 실제 retained/scratch 메모리 수명주기를 fail-closed로 통제
3. `core <- facade <- testkit` 형태로 독립 추출 가능한 배포 단위

현재 구현은 dependency direction, 순수 domain/ports, ledger의 일부 원자적 연산, 다수의 store 실패 경로에는 강하다. 그러나 다음 목적 핵심이 깨진다.

- 권장/default builder가 회계를 수행하지 않는 report-only broker를 만든다.
- live broker에 attach한 runtime scratch도 ledger를 우회한다.
- 필수 class가 manifest에서 빠지면 해당 class cap이 사라진다.
- charged store를 drop하면 실제 메모리는 해제되어도 ledger ticket은 남는다.
- 일부 store는 이미 데이터를 넣은 뒤 accounting sink를 붙일 수 있다.
- key, identity, tombstone, index 메모리가 charge 대상에서 빠진다.
- reclaim 후 in-memory spill로 넘길 때 실제 메모리는 남지만 charge는 환급된다.
- 실제 standalone 추출이 실패한다.

현재 GREEN은 “구현된 경로의 국소 계약”에 대한 증거다. 공개 API 전체가 메모리 권위를 우회할 수 없다는 증거는 아니다.

## 2. 시스템 목적과 실제 구조

```text
host adapter (Semantica, external)
        |
        v
facade: portable stores / pipelines / spill backings
        |
        v
core API: builder / broker / runtime view / control
        |
        v
application: pressure controller / scheduler
        |
        v
domain + ports: policy / ledger / tickets / abstractions

testkit -> facade -> core
```

정적 dependency direction과 pure-layer fence는 지켜진다. 문제는 compile-time direction이 아니라 **runtime authority와 lifecycle ownership이 여러 경로로 분산**되어 있다는 점이다.

## 4. Confirmed P1 findings

### P1-01. 필수 class 누락이 class cap 제거로 바뀐다

- 필수 목록: `crates/quanta-memory-platform-core/src/domain/policy.rs:147-166`
- validator는 존재하는 map entry만 검사: `core/src/domain/config.rs:191-282`
- ledger는 class entry가 있을 때만 cap 적용: `core/src/domain/ledger.rs:346-370`

재현 조건: custom manifest에서 `ArtifactCache` 같은 mandatory class 하나를 생략한 뒤 해당 class로 reserve한다.

영향: configuration error가 거부되지 않고 global/owner cap만 남는다. class isolation 기준에서는 fail-open이다.

필수 보완:

- validated policy를 total map으로 만든다.
- mandatory class 누락은 build/reconfigure에서 reject하거나 명시적 zero-deny budget으로 materialize한다.
- ledger도 미설정 class를 거부한다.

### P1-02. live runtime scratch가 live ledger를 우회한다

- `LiveProcessMemoryBroker::attach_runtime`은 `BasicRuntimeMemoryView` 반환: `core/src/api/control.rs:555-562`
- view의 scratch는 `BasicScratchAllocator`: `core/src/api/broker.rs:33-75`
- allocator는 요청값을 담은 로컬 reservation만 생성: `core/src/adapters/scratch.rs:9-27`
- release는 bool만 변경: `core/src/ports/scratch.rs:61-75`

재현 조건: live broker → `attach_runtime` → `scratch().reserve_scratch_scope(...)`.

영향: global/class/owner/execution-scratch cap과 ledger snapshot에 나타나지 않는다.

필수 보완: broker-bound runtime view와 ticket-owning scratch reservation을 도입한다. reserve는 ledger charge와 원자적이어야 하고 close/drop 정책이 명확해야 한다.

### P1-03. 권장/default builder는 enforcement가 없는 broker를 만든다

- facade `MemoryPlatformBuilder::build`: `facade/src/shared/builder.rs:75-77`
- core `build()`은 `BasicProcessMemoryBroker` 반환: `core/src/api/builder.rs:39-55`
- basic broker는 report만 보유: `core/src/api/broker.rs:78-100`
- 두 shipped example 모두 `.build()` 사용: `facade/examples/hello_world.rs:24-33`, `effective_budget_report.rs:4-8`
- live accounting은 별도 feature와 `.build_live()` 경로다.

영향: 문서와 예제를 그대로 따르면 예산 보고서는 얻지만 실제 회계/거부 권위는 없다.

외부 Semantica production composer는 `.build_live()`와 sink를 사용하므로 이 결함의 해당 경로는 피한다. 그러나 standalone 소비자 API 목적은 충족하지 못한다.

필수 보완: 기본 `build()`를 charged/live 권위로 바꾸고 report-only 결과는 `build_unenforced_report()`처럼 위험이 드러나는 이름으로 분리한다.

### P1-04. raw authority가 공개되어 builder-first/validation을 우회한다

- root re-export: `core/src/lib.rs:7-14,32-34`
- public constructors: `core/src/api/broker.rs:41-49,83-86`
- unvalidated ledger construction/policy swap: `core/src/domain/ledger.rs:237-265`
- public API test는 raw types를 고정하면서 builder-only라고 주장: `core/tests/public_api_surface.rs:17-35,94-135,267-269`

영향: validator, broker lock, scheduler, ticket-group, scratch enforcement를 우회하는 외부 API가 SemVer surface로 고정된다.

필수 보완: raw ledger mutation과 basic constructors를 crate-private로 내리거나 명시적 `advanced_unchecked` feature로 격리한다.

### P1-05. charged store drop이 ledger charge를 누수한다

- entry가 ticket 소유: payload `:28-36`, retained map `:20-27`, revocable `:13-19`, transcript `:20-26`, prepared publication `:192-197`
- facade 전체에 `Drop`/`close` implementation 없음.
- ticket도 drop-release 없음: `core/src/domain/ledger.rs:53-67`

재현 조건: charged store에 insert한 뒤 explicit delete/drain 없이 store를 drop한다.

영향: 실제 memory는 해제되지만 broker usage와 live ticket이 남아 이후 정상 allocation을 거부한다.

필수 보완: fallible `close/drain`을 1차 계약으로 만들고, scope guard/owner revocation으로 abandoned object를 회수한다. `Drop`만으로는 rebuild 중 refund 실패를 전달할 수 없으므로 명시적 close와 best-effort drop 정책을 분리해야 한다.

### P1-06. late sink attach가 charged/uncharged residency를 혼합한다

- public `new` + consuming `charged_against`: payload `service.rs:68-84`, revocable `:44-58`, transcript `:80-95`, prepared publication `prepared_publication.rs:227-260`
- retained map만 typestate builder로 이를 차단: `retained_map/service.rs:52-80`

재현 조건: uncharged 상태로 insert → populated store에 `charged_against` → 이후 charged insert.

영향: nominally charged store 안에서 기존 entry는 ticketless, 이후 entry만 charged가 된다.

필수 보완: retained map과 동일한 typestate construction을 전체 store에 적용하고 mutation 이후 mode transition을 제거한다.

### P1-07. key/identity/index/tombstone retained memory가 ledger 밖에 있다

- accounting seam은 모든 retained byte를 주장: `facade/src/shared/accounting.rs:3-9`
- retained map/revocable은 value만 `ByteSized`
- transcript는 body만 charge하고 session/message identity를 여러 map에 복제
- prepared publication은 payload만 charge하고 arbitrary identity/index를 유지

재현 조건: MB 단위 `String` key/identity와 zero-byte value/body를 넣는다.

영향: 실제 retained memory가 커져도 ledger charge는 0에 가깝다. allocator overhead 오차가 아니라 public type contract에서 빠진 byte다.

필수 보완: payload + key/identity + index + tombstone + fixed overhead를 포괄하는 `RetainedCost` 계약 또는 bounded/interned identity와 별도 metadata class charge가 필요하다.

### P1-08. transcript tombstone은 무제한이며 회계되지 않는다

- process-lifetime policy만 존재: `transcript_store/mod.rs:170-193`
- evidence map: `transcript_store/service.rs:40-46`
- truncate는 body ticket을 환급하고 evidence는 유지: `service.rs:166-212`
- stats는 active body만 계산: `service.rs:111-133`

재현 조건: unique append → truncate-to-zero를 반복한다.

영향: ledger가 0으로 돌아가도 process lifetime 동안 tombstone memory가 계속 증가한다.

필수 보완: tombstone count/byte budget, saturation behavior, idempotency horizon, 필요한 경우 durable identity store를 계약으로 정의한다.

### P1-09. reclaim → in-memory spill에서 accounting ownership이 사라진다

- revocable reclaim은 먼저 refund하고 `(Key, Value)`만 반환: `revocable_store/service.rs:144-154`
- routed spill은 accounting-neutral: `spill/service.rs:54-59`
- in-memory target은 같은 process RAM에 value를 유지: `spill/service.rs:114-131,174-185`

영향: bytes는 계속 resident인데 ledger에서 제거된다.

필수 보완: source ticket을 destination reservation으로 원자 이전하는 receipt가 필요하다. off-process durable spill과 in-memory tier를 같은 무과금 `spill` 의미로 취급하면 안 된다.

### P1-10. 실제 standalone extraction이 실패한다

- copy plan: `scripts/lib/self-hosting-manifest.sh:8-22`
- extracted verification: `scripts/extract-to-standalone-repo.sh:133-139`
- regression rail은 `tools/semgrep/qmp-regressions.yml`을 참조: `scripts/regression-guards.sh:13-18`
- copy plan에는 `tools/semgrep`과 `Cargo.lock`이 없다.

실제 명령 `scripts/extract-to-standalone-repo.sh /tmp/qmp-boundary-audit.h8nz5W`은 semgrep이 설치된 환경에서 config 누락으로 exit 7이었다. `Cargo.lock`도 새로 생성되어 추출 직후 `?? Cargo.lock` dirty 상태가 된다. 새 resolution에는 `moka 0.12.15 -> 0.12.16`, `scc 3.8.7 -> 3.8.8`, `hdrhistogram 7.5.4 -> 7.6.0` drift가 관찰됐다.

## 5. Confirmed P2 findings

### P2-01. policy vocabulary 일부가 inert다

실제 consumer census 결과:

- class/owner/group `soft_cap_bytes`: validation 외 admission/pressure/reclaim에 미사용
- class `reserved_bytes`: global floor 계산만 하고 class 보호를 예약하지 않음
- group `reserved_bytes`, `burst_percent`, `reclaim_priority`: runtime admission에 미사용
- class `reclaim_priority`: broker slow path에 연결되지 않은 helper에서만 사용

예: global 100, class A reserved 50, class B hard 100이면 B가 100을 먼저 쓰고 A의 “reserved” 50을 막을 수 있다.

보완 기준: Linux cgroup v2처럼 protection(`min/low`), pressure/throttle(`high`), hard ceiling(`max`), work-conserving weight를 서로 다른 의미로 정의한다.

### P2-02. legal borrowing 상태에서 identity reconfigure가 실패한다

- reserve/scheduler는 hard cap 초과 borrowing을 허용: `ledger.rs:346-368`, `scheduler.rs:88-96`
- reconfigure는 borrow allowance 없이 hard cap만 비교: `control.rs:415-433,465-487`

현재 policy 그대로 재설정해도 합법적 borrowed usage가 있으면 거부될 수 있다.

### P2-03. public `record_group_usage`가 scheduler와 ledger를 분리한다

- 정상 reserve/release가 이미 group usage를 대칭 갱신: `control.rs:256-319`
- 별도 public mutation: `control.rs:329-333`
- symmetric public release 없음, repo caller 없음.

호출 시 phantom/double usage가 남는다. 제거하거나 receipt 기반 reconciliation API로 바꿔야 한다.

### P2-04. ticket에 Reserved/Committed 상태가 없다

- live ticket은 ID 존재 여부만 추적: `ledger.rs:228-233`
- commit은 상태를 바꾸지 않음: `ledger.rs:407-436`
- ticket은 clone 가능.

동일 ticket의 반복 commit이 성공하고, uncommitted ticket drop은 rollback하지 않는다. `ReservationGuard -> CommittedReceipt -> Released` typestate가 필요하다.

### P2-05. live reconfigure provenance가 stale해진다

accepted reconfigure는 `report.residency`만 갱신하고 source/revision provenance는 바꾸지 않는다: `control.rs:521-551`.

### P2-06. reclaim ladder가 broker admission slow path에 없다

controller arithmetic은 존재하지만 broker reserve denial에서 reclaim/spill callback을 호출하지 않는다. 현재는 end-to-end reclaim system이 아니라 계산 helper다.

### P2-07. conformance oracle이 black-hole accounting을 배제하지 못한다

- suite는 target이 보고한 관계 위주이며 exact expected totals를 의도적으로 피함: `testkit/src/conformance/suites.rs:355-405`
- commit/finish/release 결과 일부를 무시: `:380-388,434-440`
- real target snapshot error를 balanced zero view로 변환: `testkit/src/conformance/target.rs:232-245`

항상 `Ok(ticket)`, 회계 0, rebuild 때만 reject하는 broken target이 통과할 수 있다. observation failure는 verdict error여야 한다.

### P2-08. store mutex 내부에서 외부 accounting callback을 실행한다

payload, retained map, revocable, transcript, prepared publication 모두 container lock을 잡은 채 public dyn `AccountingSink`를 호출한다.

custom sink 재진입 또는 broker→store 역순 호출 시 deadlock 가능성이 있다. two-phase versioned mutation 또는 명시적 lock-order/narrow trusted sink가 필요하다.

### P2-09. poison을 empty/zero로 위장하는 stats 경로가 있다

- payload: `service.rs:240-247`
- revocable: `service.rs:157-164`
- transcript trait stats: `service.rs:403-405`
- spill retained counts도 유사.

corrupted nonempty state가 정상 empty로 관측된다. checked observation을 trait authority로 올려야 한다.

### P2-10. optional moka/scc backings는 실제 store backing이 아니다

`MokaBacking`과 `SccBacking`은 독립 `String -> usize` index이며 `RevocableStore`/backing port를 구현하지 않고 builder에서 선택되지 않는다. feature 이름은 semantic replacement를 암시하지만 compile-only helper다.

### P2-11. durable spill 재시작 후 routed count가 틀린다

controller는 항상 count 0에서 시작하지만 redb는 기존 handle을 복구한다. reopened nonempty redb를 wrap하면 retained data와 `spilled_count`가 불일치한다.

### P2-12. facade의 확정적 scaling hazard

- payload distinct insert는 `Vec` 전체 scan으로 N개 적재가 O(N²)
- revocable full drain은 반복 `Vec::remove(0)`으로 O(N²)
- slice별 global mutex 직렬화

benchmark가 없어 실제 threshold도 정의되지 않았다.

### P2-13. uncharged mode counter가 `u64` 경계에서 조용히 손상된다

payload/revocable은 saturating add/sub를 사용한다. `u64::MAX` 크기 entry 후 1-byte entry를 넣고 큰 entry를 제거하면 1-byte live entry가 있어도 counter가 0이 될 수 있다.

### P2-14. `NoopSpillController`가 handle을 버리고 성공을 반환한다

`facade/src/spill/service.rs:43-51`의 controller는 소유권을 받은 handle을 폐기하고 `Ok(())`을 반환한다. repository production caller는 발견되지 않았지만 public `SpillController` 계약에서 성공을 durable/offloaded 상태로 해석하는 순간 데이터 유실이 된다.

보완: 이름과 반환형을 `Discard/Evict`로 분리하거나, spill target 미구성은 typed `Unsupported/Unavailable`로 실패시킨다. destructive discard는 별도 명시적 API여야 한다.

### P2-15. public bumpalo arena가 scratch budget을 우회한다

`facade/src/scratch/bumpalo.rs:1-9`는 binding/reservation/sink 없이 unrestricted `&bumpalo::Bump`를 노출한다. 현재 production caller는 없지만 `payload_store` feature가 이 dependency를 켜고 public API로 제공한다.

보완: ticket-backed scratch scope만 allocator를 노출하게 하거나, 통합 전까지 public export/feature에서 제거한다.

## 6. P3 및 proof gaps

- weighted burst share는 `(pool / total_weight) * weight`라 remainder를 의도적으로 버린다. 안전하지만 work-conserving하지 않다.
- telemetry adapter는 generic emitter 수준이고 denial/rebuild/reconfigure/spill/reclaim call site와 연결되지 않는다.
- feature matrix는 `cargo check`만 사용하여 bare-feature dead-code warning을 허용한다.
- no `benches/`, criterion, iai-callgrind, loom, fuzz target이 없다.
- Miri/loom 기반 lock-order 및 interleaving proof가 없다.
- 모든 package가 `rust-version` 미지정, `UNLICENSED`, `publish=false`; extraction/release artifact 목표가 있다면 정책 결정이 필요하다.
- legacy API는 deprecated 표시만 있고 consumer census/removal gate artifact가 없다.

## 8. SOTA 기준과 목표 설계

### 8.1 정책 의미를 분리한다

Linux cgroup v2의 모델을 기준으로 다음을 명시적으로 분리한다.

- `protected`: 다른 class/group가 침범하지 못하는 보장 또는 best-effort 보호
- `high`: pressure/reclaim을 시작하는 threshold
- `max`: allocation을 거부하는 hard ceiling
- `weight`: active consumers 사이의 work-conserving share

현재 `reserved/soft/hard/burst` 이름을 유지하려면 위 의미와 1:1 mapping, enforcement point, event를 문서와 코드로 고정해야 한다.

참조: https://cdn.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html

### 8.2 reservation을 자원 수명주기 객체로 만든다

목표 상태 머신:

```text
ValidatedPolicy
    -> ReservationGuard (drop before commit = rollback)
    -> CommittedReceipt (exactly one live owner)
    -> transfer(destination) OR release/close
    -> Released
```

- clone 가능한 raw ticket를 권위로 쓰지 않는다.
- store entry와 spill tier가 receipt ownership을 명시적으로 이전한다.
- store close가 실패할 수 있는 경우 explicit close를 authoritative path로 둔다.
- abandoned guard의 rollback은 RAII로 보장한다.

관련 선례:

- DataFusion `MemoryPool`/`MemoryReservation`: allocate 전 grow, 실패 시 증가 없음, shrink/drop lifecycle  
  https://docs.rs/datafusion/latest/datafusion/execution/memory_pool/trait.MemoryPool.html
- Tokio semaphore permit: permit lifetime과 drop을 capacity 반환에 결합  
  https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html

### 8.3 retained cost를 total cost로 정의한다

각 entry charge는 최소 다음을 포함한다.

```text
payload/body
+ key / identity
+ index and tombstone bytes
+ implementation-defined fixed overhead
+ allocator slack policy
```

정밀 allocator bytes와 semantic estimated bytes는 별도 metric으로 둔다. allocator telemetry는 advisory이되 semantic charge의 누락을 정당화하면 안 된다.

### 8.4 spill은 tier transfer transaction이어야 한다

권장 순서:

1. destination capacity/reservation 확보
2. destination write 및 durable commit
3. destination ownership receipt 획득
4. source entry 제거
5. source receipt release

중간 실패는 source 또는 destination 한쪽이 authoritative owner가 되도록 복구해야 한다. in-memory tier는 process RSS가 줄지 않으므로 off-process spill과 같은 회계 정책을 사용할 수 없다.

### 8.5 concurrency proof rail을 추가한다

- Loom: ticket transition, reserve/release/reconfigure, spill transfer의 interleaving model
- Miri: unsafe/alias/data-race execution 검사
- adversarial reentrant sink와 poisoned lock contract
- property tests: 임의 operation sequence 후 class/owner/kind/ticket balance

참조:

- https://github.com/tokio-rs/loom
- https://github.com/rust-lang/miri/

### 8.6 public API와 SemVer를 권위 경계로 취급한다

raw constructors를 이미 public API test가 고정하고 있으므로 제거는 compatibility 판단이 필요하다. major break 또는 staged deprecation/feature quarantine가 필요하다.

참조: https://doc.rust-lang.org/cargo/reference/semver.html
