# quanta-memory-platform 감사 보고서

## 1. 총평

이 워크스페이스는 핵사고날 아키텍처와 회계 SSOT(AccountingLedger)를 중심으로 한 의도가 명확하고 깔끔하게 구조화된 초기 단계 코드베이스이지만, **핵심 안전 메커니즘 다수가 문서·타입으로만 약속되고 실제 코드 경로에서는 미배선(unwired)된 "스캐폴딩" 상태**다. 가장 큰 위험은 (1) 전역 하드 한도(global_hard_limit_bytes)가 reserve에서 전혀 강제되지 않고, (2) 프리셋/매니페스트 경로로 만든 모든 브로커가 클래스 예산이 비어 있어 클래스 캡이 무력화되며, (3) 파사드 스토어 전체가 원장 SSOT와 단절되어 캡이 어떤 실제 스토어 바이트도 제어하지 못한다는 점이다. 정확성 측면에서는 ReservationTicket 이중 release로 인한 조용한 회계 손상, live reconfigure의 fail-open 구멍이 두드러진다. 문서가 코드보다 앞서 있어("consults the scheduler", "validated", "broker slow path knows where to reclaim") 리뷰어·통합자를 오도할 위험이 반복적으로 나타난다.

## 2. 심각도별 핵심 발견

### High

- **전역 하드 한도가 reserve에서 강제되지 않음** — `domain/ledger.rs:238`
  영향: 쿼터 없는 owner가 예산 없는 class에 무제한 charge 가능(프리셋 기본 상태). 플랫폼의 가장 중요한 한도가 advisory.
  수정: reserve에서 `snapshot total + bytes > global_hard_limit_bytes`이면 Capacity로 거부(headroom 반영).

- **프리셋/매니페스트 브로커가 클래스 예산 없이 생성됨** — `domain/policy.rs:226` (`for_preset` → `ResidencyPolicy::new` 빈 classes map)
  영향: 모든 의도된 생성 경로의 브로커에서 클래스 하드 캡이 절대 발동하지 않음(ledger.rs:258 `if let Some(budget)`가 항상 None).
  수정: `for_preset`가 14개 mandatory 클래스 기본 예산을 채우거나, validate_residency가 비-trivial 프리셋의 빈 classes를 거부.

- **파사드 스토어 회계가 원장 SSOT와 완전 단절** — `facade/src/shared/builder.rs:33`
  영향: `MemoryPlatformBuilder::build()`는 report-only 브로커만 반환. Simple* 스토어는 private 카운터에 charge하며 ledger.reserve를 호출하지 않음 → 글로벌/owner/class 캡이 실제 스토어 바이트를 전혀 제어 못함. binding의 class/owner는 장식.
  수정: Simple* 스토어에 라이브 브로커(또는 reserve/commit/release 포트) 핸들을 주입해 `binding.class/owner`로 라우팅, 혹은 "비예산 스토어"임을 강하게 문서화.

- **ReservationTicket 이중 release로 조용한 회계 손상** — `domain/ledger.rs:296` (commit/release는 `&ticket`, ticket은 Clone)
  영향: 동일 ticket을 두 번 release하면 `saturating_sub`가 underflow를 가려 class/owner/context 카운터가 진실값 아래로 drift, 불변식 1·2 위반. 공개 API로 도달 가능.
  수정: 원장이 발급/해제 ticket id를 추적(HashSet)하거나 ticket을 값으로 consume, 미지/이미 해제된 id는 InvalidState로 거부.

- **try_live_reconfigure가 새 정책에서 누락된 클래스의 사용량을 무한 캡으로 둠(fail-open)** — `api/control.rs:161`
  영향: 라이브 reconfigure가 현재 바이트를 보유한 클래스를 정책에서 누락시키면 캡 검사 통과 → swap_policy 후 그 클래스는 하드 캡 없이 무제한 성장. 불변식 5/3 무력화.
  수정: `new_policy.classes`가 아니라 `snapshot.class_usage` 키를 순회, live usage 클래스가 새 정책에 없거나 usage 미만이면 거부.

### Medium

- **live reserve 문서가 수행하지 않는 스케줄러 admission을 약속** — `api/control.rs:65` (본문은 `ledger.reserve`만 호출, owner→group 매핑 자체가 데이터 모델에 부재)
  영향: weighted fair-share/starvation 보호가 reserve 경로에서 전혀 작동 안 함. fake는 group cap을 강제해 실/가짜 브로커가 발산하나 conformance가 group을 구성하지 않아 미검출.
  수정: reserve에 group admission 구현(또는 거짓 문장 삭제), 두 타겟에 group-cap 거부 conformance 케이스 추가.

- **try_live_reconfigure가 owner 쿼터 하드 캡을 현재 owner 사용량과 비교하지 않음** — `api/control.rs:161`

  수정: class 검사를 미러링해 `owner_quotas` vs `snapshot.owner_usage` 루프 추가.

- **비-라이브 build()가 validate_residency를 우회** — `api/builder.rs:36`
  영향: 구조적으로 무효한 예산(reserved>soft>hard, 글로벌 floor 위반)이 통과해 불가능한 정책을 광고하는 report 생성. 두 builder 진입점이 합법 예산 정의에 불일치.
  수정: build() 내부에서 `validate_residency(&manifest.residency)?` 호출(build_live/from_report와 동일).

- **validate_residency가 resource_groups를 전혀 검증 안 함** — `domain/config.rs:187`
  영향: 역전된 그룹 캡(soft>hard)이나 과대 그룹 reserved가 통과(런타임상 대부분 inert이나 문서 불변식 3 위반).
  수정: 각 ResourceGroup의 reserved<=soft<=hard 검증, 글로벌 floor에 그룹 reserved 포함.

- **클래스/owner 하드 캡이 글로벌 한도 이하인지 검증 안 함** — `domain/config.rs:187`
  영향: 4GiB 글로벌에 10GiB 클래스 캡 선언이 통과 → reserve의 글로벌 미강제와 결합 시 글로벌 초과 예약 허용.
  수정: 어떤 class/owner hard_cap도 global_hard_limit 초과 시 거부.

- **BasicPinRegistry가 poison된 lock에서 panic(워크스페이스 fail-closed 규약 위반)** — `ports/pin.rs:49,57,69` (3개 `.expect()`)
  영향: 유일한 프로덕션 PinRegistry 어댑터가 다른 lock 사이트와 달리 panic; dependent_count는 u64라 에러 채널 부재. FFI 경계 unwind/프로세스 abort 가능.

## 3. 차원별 요약

**SE(소프트웨어 공학):** 가장 반복되는 패턴은 "문서가 코드보다 앞서기"다 — reserve의 스케줄러 협의, PressureThresholds "validated", 원장 "fail-closed", insert_checked의 reserve/release choreography가 모두 코드와 불일치하고 이를 잡는 테스트가 없다. fail-closed-no-panic 규약은 BasicPinRegistry 한 곳만 위반한다. 에러 별칭 붕괴, 미사용 공개 생성자, ticket id 장식 등 API 정직성·일관성 이슈가 다수이나 대부분 런타임 무해.

**성능:** 모든 성능 발견은 실제 알고리즘 결함이나 카디널리티 의존이고, 대상이 명시적으로 "Simple" 참조 스토어 또는 테스트 인프라라 대부분 medium-low다. 핵심은 read 경로의 불필요한 3-맵 deep clone(lock 보유 중), 페이로드 키 전체 복제(2× 메모리), 선형 스캔/O(n²) reclaim/플랫 트랜스크립트 Vec다. 정확성 영향은 없다.

**아키텍처:** 핵사고날 의도는 명확하나 "feature-sliced", "SSOT behind a lock", "durable spill", per-class isolation 같은 핵심 약속이 미배선 스캐폴딩이다. 기능 플래그가 코드를 게이트하지 않아 슬라이싱 계약이 거짓이며(3개 크레잇 공통), 서드파티 백킹은 전부 dead code다. 가장 무거운 것은 파사드가 원장 권위를 우회하고 프리셋이 클래스 예산 없이 나온다는 계층 단절이다.

**기능 누락:** 광고된 능력과 구현 사이 갭이 광범위하다 — 전역 한도/클래스 캡/그룹 캡/soft 캡/ExecutionBudget/scratch 회계/spill 복원/reclaim 구동/override 레이어(파사드)/conformance facade suite가 선언·문서화되었으나 실제 강제·실행 경로가 없다. 스케줄러 전체가 reserve에서 호출되지 않는 독립 미배선 서브시스템이다.

**정확성·안전성:** 진짜 silent-corruption은 ReservationTicket 이중 release(불변식 1·2 위반)와 live reconfigure의 누락 클래스 fail-open이다. 둘 다 공개 API로 도달 가능하나 호출자 오용/운영자 액션을 요한다. 실/가짜 브로커의 캡 deny 발산은 conformance 오라클 신뢰도를 훼손한다. i64 truncation·×100 saturate는 비물리적 입력에서만 발동하는 nit다.
